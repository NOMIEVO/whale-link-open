# 手机 ↔ 挂件 数据链路协议（时间 / 传感器 / 投屏）

> 适用：本仓库 `firmware/` + `android/`，ESP32-C3（BLE 5，NimBLE GATT server）
> App：Android（Java，minSdk 26）
> 余额特征（0x02）沿用产品侧的 `deepseek-balance-whale-bluetooth` 协议定义，本文件不重复。

## 1. GATT 布局

服务 UUID：`4f7c0001-1e2d-4a5b-8c3f-9d0e1f2a3b4c`

| 尾号 | 特征 | 属性 | 方向 | 用途 |
|---|---|---|---|---|
| `0x02` | Balance | Write / WriteNR | 手机 → 设备 | 余额快照（已有，40 B） |
| `0x03` | Request | Notify | 设备 → 手机 | 请刷新（已有，1 B） |
| **`0x04`** | **Time** | Write / WriteNR | 手机 → 设备 | 时间同步，8 B |
| **`0x05`** | **Sensor** | Write / WriteNR | 手机 → 设备 | 传感器帧，24 B |
| **`0x06`** | **Frame** | Write / WriteNR | 手机 → 设备 | 投屏分块，16 B 头 + payload |

全部小端。长度不足或版本号不符一律丢弃——多半是 MTU 没谈拢被截断。

连接参数：日常 100–200 ms / latency 4 省电；**投屏开启时切到 15–30 ms / latency 0**，否则一包一个连接事件，吞吐会被压到十分之一。

## 2. Time 帧（8 B）

```
u8  version   = 1
u8  flags     bit0 = 时间有效, bit1 = 带时区
i16 tz_min    本地时区相对 UTC 的分钟数（北京 = +480）
u32 unix_sec  UTC 秒
```

手机连上就发一次，之后每 60 秒重发。设备收到后把它作为走时基准（`esp_timer` 累加），重启或深睡后归零，等下一次同步。

## 3. Sensor 帧（24 B）

```
u8  version   = 1
u8  kind      见下表
u8  flags     bit0 = 本帧有效
u8  seq       序号（只用于统计丢包，不重传）
u32 t_ms      手机侧相对时间，自本次连接起（毫秒）
s32 v[3]      三个值，单位随 kind
u32 aux       附属字段，随 kind
```

| kind | 含义 | v[0..2] 单位 | aux |
|---|---|---|---|
| 0 | 加速度 | 1e-3 m/s² | — |
| 1 | 角速度（陀螺仪） | 1e-3 rad/s | — |
| 2 | 重力 | 1e-3 m/s² | — |
| 9 | 位置 | 纬度·1e7 / 经度·1e7 / 海拔 cm | bit0-15 速度 cm/s，bit16-31 航向 0.01° |

固定点整数，不用浮点：跨语言编码不会有字节序和精度歧义。

采样率默认 10 Hz（100 ms 一帧），加速度与陀螺仪各一帧 → 约 480 B/s，占链路不到 5%。

## 4. Frame 帧（投屏，16 B 头 + payload）

```
u8  version   = 1
u8  type      0 = BEGIN, 1 = CHUNK, 2 = END
u8  fmt       0 = RGB565 + RLE, 1 = JPEG（预留）
u8  flags     bit0 = 整帧（非差分）
u16 w         图像宽（BEGIN 有效）
u16 h         图像高（BEGIN 有效）
u16 seq       帧序号，回绕
u16 idx       块序号，从 0 开始
u16 total     本帧总块数
u16 len       本包 payload 字节数
```

- 分块大小按协商 MTU 减 3 字节（ATT 写头）再减 16（本头）。MTU 517 时 payload 上限 498。
- 设备按 `seq` 累积，`idx` 单调递增（Write No Response 在 ATT 层保序，不会乱序到达）；收到 `END` 且块数齐全才开始解码。
- 单帧总长上限 **40 KB**（`120×160` 的 RGB565 是 38400 字节，正好放得下）；超出直接丢弃并等下一帧。

### RGB565 + RLE 编码

token 首字节 `h`：

- `h & 0x80` → run：重复像素，长度 = `h & 0x7F`（1–127），后跟 2 字节 RGB565
- 否则 → raw：原始像素，个数 = `h & 0x7F`（1–127），后跟 `n × 2` 字节

最坏膨胀 1.5×，UI 截图通常 3–8× 压缩。RLE 是无损的，编码后仍超过 40 KB 时只能丢帧（手机端会记一条日志），用户手动降一档分辨率即可。

### 为什么不用 JPEG

JPEG 压缩率更好，但设备端要额外拉 `esp_jpeg` 组件、解码需要整帧输出缓冲，C3 上内存和 Flash 都更紧。RLE 解码是逐行的，可以直接写进 LVGL 的图像缓冲，零依赖。先用 RLE 把链路跑通，真需要更高质量再换。

## 5. 设备侧渲染约束

- 投屏缓冲：`120 × 160 × 2 = 38.4 KB`（默认档），显示时 `lv_image_set_scale(512)` 放大到 240×320。
- 解码在**主循环**做，不在 BLE 回调里做——回调跑在 host 任务，碰 LVGL 必须持 `bsp_lvgl_lock()`，而且在里面做 38 KB 的活会直接拖垮连接事件。
- 投屏期间暂停鲸鱼呼吸动画（`lv_anim_delete`），刷新预算全给画面。
- 内存不足时自动退到 `96 × 128`（24 KB）。

## 6. 帧率预期（实测口径）

BLE 在 C3 上有效吞吐约 100 kbps（12.5 KB/s），连接参数放快后可达 20–30 KB/s。

| 分辨率 | RLE 后典型大小 | 连接参数放快后 | 省电参数下 |
|---|---|---|---|
| 120×160 | 6–12 KB | 1–3 fps | 0.5–1 fps |
| 96×128 | 4–8 KB | 2–4 fps | 0.8–1.5 fps |
| 160×213 | 10–20 KB | 0.8–2 fps | 0.3–0.6 fps |

**这不是"投屏"，是"低帧率画面回传"。**做产品文案时别写"实时投屏"。

## 7. 文件传输（手机 → 设备 Flash，v2 扩展）

> ⚠️ **本章的「4 个 1MB 槽位」是 v1 的做法，已被第 9 章的变长分配取代。**
> 报文格式完全不变，只有 `slot` 字段的语义从「槽位 0–3」变成「条目索引 0–15」。
> 新实现请直接读第 9 章，本章保留作为格式参考。

复用 Frame 特征族的 16 字节块头，走独立的 **File 特征**
（UUID `4f7c0007-1e2d-4a5b-8c3f-9d0e1f2a3b4c`，可写 + notify）。
`storage` 分区一整块 4.94 MB，由 `whale_file.c` 分配，元数据存 NVS。

### 写方向（手机 → 设备）

```
[0]  ver = 1
[1]  cmd       1=BEGIN 2=DATA 3=END 4=LIST 5=DELETE 6=VERIFY
[2]  slot      0–3
[3]  保留
[4]  u32 total_len   文件总字节数
[8]  u16 idx         块序号：BEGIN=0，DATA 从 1 连续递增
[10] u16 total_blocks（含 BEGIN 和 END）
[12] u16 plen        本包净荷字节数
[14] u16 保留
```

- **BEGIN**（idx=0）：净荷 = `crc32(u32 LE) + 文件名(12B, NUL 填充, ASCII)`
- **DATA**（idx=1..N）：净荷 = 文件内容切片，块大小 = `MTU-3-16` 再留 4 字节余量
- **END**（idx=total-1）：净荷空，但**包长必须 > 16**（补 1 字节占位）——
  设备对 ≤16 字节的包直接丢弃
- `idx` 断裂或长度不符 → 设备 notify status=6，整次作废，手机从 BEGIN 重来
- LIST/DELETE/VERIFY 单包即命令，同样要补 1 字节占位

### 读方向（设备 → 手机，notify，28 字节定长小端）

```
[0] ver [1] status [2] slot [3] 保留
[4] u32 written  [8] u32 crc  [12] u32 total_len  [16..27] name(12B)
```

| status | 含义 |
|---|---|
| 1 | 接受 BEGIN |
| 2 | 进度（每 32 块一次） |
| 3 | 完成 / 校验通过（END 回读或 VERIFY 单独触发） |
| 4 | 完成但 CRC 不符 |
| 5 | 拒绝（槽位/长度非法） |
| 6 | 序号断裂 |
| 7 | 设备写 Flash 失败 |
| 8 | 槽位信息（LIST 逐槽回报，name/total_len 有效） |
| 9 | 已删除 |
| 10 | 槽位为空 |

**手机必须订阅 CCCD**（写 0x0001 到 0x2902 描述符）才能收到回报；
订阅和特征写要在同一条串行队列里做，否则会撞 Android GATT busy。
本地 CRC 对 ≠ 落盘对，最终结论以设备回读校验（status=3/4）为准。

### 容量与速度

- 每槽上限 1MB；擦除只擦已用扇区，不整擦 1MB
- 传输速率同投屏快档（20–30 KB/s），1MB 约 40–60 秒

## 8. 按需挂载（设备发请求，手机送一张，v3 扩展）

第 7 章是「手机主动推」，本章方向反过来：**设备说要哪一张，手机才送哪一张**。
用途是让设备访问远超自身 Flash 容量的资源库（比如手机相册 24MB+ 的照片）。

### 为什么不能"整库同步进设备"

| 约束 | 实测值 | 后果 |
|---|---|---|
| storage 分区 | 4.94 MB（4×1MB 槽位） | 24MB 装不下 |
| BLE 吞吐 | 约 25 KB/s | 24MB 要 16 分钟 |
| 可用堆 | 约 33 KB | 240×320 RGB565 = 150KB，内存也装不下 |

所以设备端的定位是**缓存窗口**而不是镜像：手机是资源库（容量不受限），
设备只保留最近用到的 4 张。

### 上行请求（设备 → 手机，Request 特征 notify）

复用已有的 Request 特征（`4f7c0003-...`），靠首字节区分：

```
[0]=1                     请查一次余额（既有）
[0]=2 [1]=slot [2..3]=idx 请送第 idx 号资源到槽位 slot（小端 u16）
```

设备端没有 CCCD 订阅时 notify 会失败，所以**手机必须订阅 Request 特征**。

### 下行数据（手机 → 设备，File 特征，复用第 7 章流程）

手机把照片解码、等比缩放到 160×213 以内、转 RGB565，再拼 12 字节头：

```
[0..3]  magic "WHLP"（小端读作 0x504C4857）
[4..5]  w (u16 LE)
[6..7]  h (u16 LE)
[8]     fmt，0 = RGB565 小端
[9..11] 保留
[12..]  紧密排列的 RGB565 像素，无 padding
```

然后走标准的 BEGIN/DATA/END 推进请求里指定的槽位。

**像素必须连续无填充**：设备会把这个槽位整体 `esp_partition_mmap` 进
DROM 地址空间，直接当 LVGL 的图像源 —— 有 padding 就得额外拷一份，
而 150KB 拷不进 33KB 的堆。这是「大图能显示」的唯一路径。

### 设备端行为

1. 长按 OK → 序号自增，槽位 4 个轮转，发 `[2][slot][idx]`
2. 收到 END 且 CRC 校验通过 → 认头部 magic → mmap → 整屏显示
3. 短按 DOWN → 收起画面并解除映射
4. 要写某个槽位之前，如果它正在显示，先撤图撤映射再擦 —— 否则 LVGL
   会读到擦除后的 0xFF

### 时序

| 步骤 | 耗时 |
|---|---|
| 设备按键 → 手机收到请求 | 瞬时 |
| 手机扫相册 + 解码 + 缩放 + 转码 | 100–500 ms |
| BLE 传 38KB（120×160 RGB565） | 约 1.5 s |
| 设备落盘 + 回读 CRC + 显示 | 约 200 ms |

**翻一张约 2 秒**。这个体验适合「选一张看一眼」，不适合做幻灯片播放。

## 9. 存储布局改为变长分配（v4，取代第 7 章的「4×1MB 槽位」）

第 7 章写的「4 个 1MB 槽位」是 v1 的做法，v4 已废弃。分区表从来没切成 4 份
—— `storage` 一直是一整块约 4.94MB 的分区，切分是 `whale_file.c` 的软件行为。
v4 把这一步也去掉了：

| | v1（4×1MB 固定槽位） | v4（一个池子 + 变长分配） |
|---|---|---|
| 分区 | 一整块 4.94MB | 不变 |
| 切分 | 程序里硬切 4 份等长 | 无固定切分，按需分配 |
| 单文件上限 | **1MB** | **约 4.9MB**（受池子大小） |
| 38KB 照片占多少 | 1MB（浪费 96%） | 40KB（按 4KB 向上取整） |
| 条目数 | 4 | **16** |
| 删中间文件后 | 空间立刻可复用 | 留空洞，需 COMPACT 整理 |

### 为什么不能直接用 LittleFS / SPIFFS

零拷贝显示依赖 `esp_partition_mmap` 把 flash 映射成内存地址给 LVGL 直读
（C3 只有 ~33KB 可用堆，240×320 RGB565 整屏 150KB，拷内存必然失败）。
日志结构文件系统**不保证文件数据物理连续**，跨页就没法一次映射
—— 所以必须自己管连续区段。这是整个设计的地基，不是可选项。

### 分配规则

- 区段起点按 **4KB**（扇区）对齐
- **first-fit**：按偏移升序扫已用区段，填第一个够大的空隙
- 写入同一索引且新长度不大于旧长度 → **原地覆盖**（不搬数据、不新增碎片）
- 新长度更大 → 先算新位置再释放旧区段；分配失败则旧元数据原样保留
- 校验通过才写 NVS；失败/中断则清掉该条目（旧内容已被覆盖部分，不再可信）

### mmap 的对齐细节（v4 新增）

区段只保证 4KB 对齐，而 `esp_partition_mmap` 要求 offset 按 **64KB MMU 页**对齐。
做法：向前取整到页边界，映射长度覆盖「页内偏移 + 数据长度」，返回给上层的
指针补上这段页内偏移 —— 调用方拿到的是数据的首地址，感知不到对齐。

### 协议变更（v4）

`slot` 字段含义从「固定槽位号 0–3」变成「**条目索引 0–15**」，报文字节布局不变。

新增命令：

| cmd | 含义 |
|---|---|
| 7 | COMPACT 碎片整理 |

新增状态码：

| status | 含义 |
|---|---|
| 11 | 整理完成，`total_len` 字段带整理后的最大可分配空闲字节 |
| 12 | 整理失败（多半还有区段正被 mmap，先收起图片） |
| 13 | **列表结束**，`slot` 字段 = 条目数，`total_len` = 最大可分配空闲字节 |

**LIST 语义也变了**：v1 逐槽回报（含空槽 `status=10`），16 条连续 notify 容易
把 NimBLE 的 mbuf 压爆。v4 只回报**有内容的条目**，末尾补一条 `status=13`
带汇总。手机据此就知道「有哪些」和「还能放多大」，不用靠超时猜。

### 何时需要 COMPACT

删掉一个夹在中间的文件后，它的空间和末尾空闲不连续。此时：

```
池子: [照片A 40KB][已删 800KB 空洞][照片B 40KB][     空闲 4.1MB      ]
想存 1MB 新文件 → 失败（最大连续空闲只有 4.1MB，够；但如果空洞后面还有东西就不够）
```

只要「总量够但没有够大的连续段」就要整理。整理把后面的文件整体前移，
按 2KB 缓冲逐块擦+读+写，1MB 约 1–2 秒。**整理期间不能有区段处于 mmap 状态**
（否则 LVGL 会读到搬了一半的字节），设备端会自动先撤图再整理。
